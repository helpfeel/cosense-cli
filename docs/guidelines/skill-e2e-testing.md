# Agent SkillのE2Eテスト手順

subagentにタスクを依頼して、手順書だけを頼りにワークフローを完遂できるか検証する手順。
実装したAIエージェント自身がCLIを直接叩いても、配管の疎通確認にしかならない。実装の全コンテキストを持っているため、手順書の不備に気づかず乗り越えてしまう。

## いつ実行するか

変更の度に自動では実行しない。実行する価値があると判断したら、ユーザーに提案して合意を得てから始める。
価値があるのは、手順書のワークフロー構成に影響する変更（手順の追加・組み替え、新コマンドの組み込み等）。文言の手直しや、挙動を変えないリファクタでは提案しない。

## subagentへの指示のやり方

### modelはSonnetを指定する

賢いmodelは手順書の不備を自力で乗り越えてしまい、手順書の検証にならない。

### 変更した方のCLIとskillを使わせる

ユーザーがマシンにインストールしているCLIやplugin版skillではなく、検証対象のworktreeにある`skills/cosense/`と`bin/cosense`を使わせる。`cosense <command>`を`<worktree>/bin/cosense <command>`に読み替える指示をプロンプトに含める。

### 情報源を制限する

許可するのはskillディレクトリ配下のファイル、CLIの`--help`出力、コマンドの実行結果だけ。以下は明示的に禁止する。実装コードやgit履歴を読めば、手順書が無くても正解できてしまう。

- リポジトリのソースコード(src/等)・docs/・README・.dev/・CLAUDE.md
- 過去の会話memory
- gitコマンドの実行

禁止で塞げるのは自分で読みに行く経路だけ。エージェント実行環境が最初から渡す情報は作業後のインタビューで拾う。

### タスク文で対象機能をほのめかさない

検証したい機能のコマンド名やヒントをタスク文に書かない。手順書だけでそこへ誘導できるかが検証対象。
例: replaceLinksの検証では「ページのタイトルを◯◯に変更してください」とだけ依頼し、「他ページからのリンクが切れないように」とは書かない。

### 推測で補わせない

手順書と`--help`を読んでも分からない事は、推測で補わずに「分からなかった」と報告するよう指示する。自力補完で手順書の穴が隠れるのを防ぐ。

### 報告形式を指定する

以下を時系列で報告させる。3つ目の申告が手順書の曖昧さの検出器になる。

1. 読んだ手順書ファイルと、従った手順の番号
2. 実行したコマンド列と、それぞれの結果の要点
3. 判断に迷った箇所、手順書に書かれていなくて困った箇所

## テスト環境

ローカル開発環境か、scrapbox.ioに用意したテスト用projectを使う。どちらの環境のどのprojectを使うかは、テスト実行前にユーザーに質問して決める。

## シナリオ設計

- シナリオは人間が指示しそうな抽象的なタスクとして設計し、そこから正しい手順に推論で辿り着けるかを検証する。引数の受理やエラー表示のように、コードを読めば検証できる事は主要な検証対象ではないが、発見した問題は報告する
- 正常系だけでなく、手順書に書いた注意点が実際に機能するかを、その罠を踏む状況を意図的に作って検証する。例: タイトル衝突時のauto-suffixへの注意書きは、衝突相手となる既存ページを用意した上で改名を依頼して検証する
- シナリオ案は複数作り、実行前にAskUserQuestionで提示してユーザーに選んでもらう。観点の不足や偏りを実行前に人間が補えるようにする
- fixture（対象ページ・リンク元ページ・衝突相手ページ等）は、テスト対象の手順の外側で事前に作っておく。タスク文と同様に対象機能をほのめかさず、テストをしている事も悟られないように文言に気をつける

## 作業後にインタビューする

subagentのcontextには、エージェント実行環境が最初から渡す情報（project instructions、memoryのindex、git status等）がある。読む操作を伴わないので禁止できず、transcriptにも残らない。作業が終わったらsessionを閉じる前にインタビューし、判断の根拠を聞き出す。成功した場合も失敗した場合も行う。

聞き出す観点:

- 各判断の根拠がどの情報源か。タスク文・手順書の記述・`--help`・コマンド実行結果・質問へのユーザー回答・エージェント実行環境の提供情報・事前学習知識・仮定、に分類させる
- 不明点を仮定で補った事は何か。「推測で補わせない」指示はsubagentが推測と自覚できた箇所にしか効かないので、作業後のインタビューでも拾う
- 必要だったが見えなかった・使えなかった情報は何か。手順書に足すべき記述の候補になる
- 手順書・`--help`・実行結果が食い違った箇所はなかったか。あればどれを採用したか。乗り越えられていても、食い違い自体が手順書の修正候補になる

回答は後付けの説明になりうるので、内省の忠実な記録ではなく原因切り分けの証言として扱い、transcript監査と突き合わせる。
成否に影響した判断の中に、エージェント実行環境の提供情報・事前学習知識・仮定なしには到達できないものが出てきたら、その回は手順書だけで完遂できた証拠にならない。

検出した穴をすべて手順書で埋めるとは限らない。安定して正しく補われる穴まで埋めると、過剰な詳細化でskillの応用力を損なう。補われ方が安定して正しいかは推測を禁じたこのテストからは観測できないので、埋めるかどうかは穴ごとにユーザーと判断する。埋める場合の修正先（CLIかSkillか）の切り分けは`docs/guidelines/cli-vs-skill.md`を参照。

## 結果の検証

subagentの自己報告を鵜呑みにせず、2つの独立確認を行う。

### transcriptログのtool呼び出し列を監査する

transcriptを丸ごと読むとcontextが溢れるので、tool呼び出し（tool名と主な引数）の列だけを抽出して読む。

見る点:

- 禁止した情報源を読んでいないか、gitを叩いていないか
- コマンドの実行前に`--help`を読んでいるか
- コマンド列が自己報告と一致するか

### 最終状態の実データを確認する

readPage等で対象ページを直接読み、意図した変更が反映されているか、巻き込むべきでないページが無傷かを確認する。
